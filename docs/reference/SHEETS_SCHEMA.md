### ⚠ Дата — колонка 0, но заголовок «А»
`new Date()` НЕ парсит `ДД.ММ.ГГГГ`. Использовать `newApplicationsClient.parseFormDate` (умеет
русский формат + ISO, отвергает мусор). `rowsToApplications` фолбэчит submitted_at на col0.

### ⚠ ДВА пути чтения заявок — НЕ путать
- **`formFieldMapper.mapRow(header, row)`** — БОГАТЫЙ (для карточки/инбокса). Даёт:
  `applicant.{name(col3), phone(col1), inn(col8)}`, `manufacturer.{name(col9), country(col10)}`,
  `legal_entity`(=col2 **ТИП** ИП/ОсОО), `l_e_country`(col4), `tnved_text`, `items[]`, `brand`,
  `age`, `submitted_at`. **ИСПОЛЬЗОВАТЬ ЭТОТ** для имени клиента и полей карточки.
  Путь инбокса: `workQueueService.newApplications()` → mapper → `applicant`(имя), `legal_entity`(тип).
- **`newApplicationsClient.rowsToApplications`** — ПРОСТОЙ. `phone`(col1),
  `legal_entity`(**col2 = ТИП «ИП», НЕ имя!**), `submitted_at`(col0). ⚠ Его `legal_entity` — это
  ТИП, а не название клиента. НЕ использовать как имя для матчинга.

## 2. «Декларация» → вкладка **`Лист1`** (~1044 строки) — источник истины по заказам

Env: `DECLARATION_SHEET_NAME=Лист1` (⚠ по умолчанию код ставит `Sheet1` — ДОЛЖНО быть `Лист1`,
иначе 0 строк). `DECLARATION_SHEET_ID` — id таблицы.

### Раскладка ЧТЕНИЯ живого листа (`workQueueService`, operator-confirmed)
| Кол | idx | Поле |
|-----|-----|------|
| **J** | 9  | **Номер тел** (первичный ID клиента) |
| **N** | 13 | **Статус** |

Остальные колонки листа НЕ подтверждены операторами (см. память `declaration-schema-status`:
подтверждён только N=Статус; K=исполнитель провизорно; A/G неизвестны; B–J/L/M — не разобраны).

### ⚠ РАСХОЖДЕНИЕ чтение vs запись — источник багов
`config/constants.js` `DECLARATION_SHEET_COLUMNS` описывает ДРУГУЮ 7-колоночную раскладку A→G
для АППЕНДА новых строк (Approved Draft Execution):
`A payment_date · B payment_amount · C client_name · D document_type · E phone · F notes · G status`.
Плюс `DECLARATION_STATUS_COLUMN` по умолчанию `G`. **Это НЕ совпадает с живым листом (J/N).**
При работе с ЖИВЫМ листом — только J=phone(9), N=status(13). A–G — легаси/аппенд, не читать по нему.
(См. память `combat-test-findings`: «status column config bug G vs N».)

### 7 канонических статусов (не переводить/не переименовывать — память `approved-statuses-verbatim`)
`Запустить` · `Ждем макет` · `На согласовании` · `Ждем оригинал` · `Оригинал получен` ·
`Завершен` · `Отменен`.

## 3. Матчинг заявка ↔ Декларация ↔ WhatsApp
- Ключ клиента = **телефон** (matchKey = последние 9 цифр локально), + юр.лицо как 2-й ID
  (память `client-entity-model`). Телефон Декларации иногда ненадёжен → фолбэк матч по ИМЕНИ
  (`declNameIndexFromRows`/`normClientName`), имя берём из `applicant.name` (col3), НЕ из типа.
- Одна сущность повторяется в нескольких строках; лаборатории работают не по порядку
  (память `order-identity-model`). При неоднозначности — показать оператору выбор (мульти-матч).
- WhatsApp: phone = WA (частичное совпадение); LID резолвится в номер через `lid_mappings`
  (см. `whatsapp-auto-responder`/`applyStoredMappings`).

## 4. Прочие источники
- **`whatsapp_messages`** (Mongo) — вся переписка (обе стороны), пишет web.js. Поля:
  `direction`, `body`, `from_phone`, `phone_key`(9-значный ключ), `lid`, `provider_message_id`,
  `received_at`, `is_group`, `attachments`. Читать историю отсюда.
- **Gmail** — канал ТОЛЬКО лаборатории; клиентов НЕ достаёт (память `client-comms-channels`).
  Привязка письма к клиенту/номеру WhatsApp (по возрастанию уверенности):
  1. название компании / ИП-ОсОО (имя клиента) совпадает с ТЕМОЙ письма;
  2. email лаборатории;
  3. ⭐ номер WhatsApp клиента встречается в ПЕРВОМ письме треда — в тексте, вложениях или
     таблицах (макет/пакет для лаборатории обычно содержит номер) → максимальная уверенность.
  Показывать: последнее письмо (тема, дата, отправитель, краткое содержание) + «нужен ли наш ответ».
